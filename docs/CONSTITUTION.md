# プロジェクト原則

**バージョン**: 4.1.0
**最終更新日**: 2026-05-03
**ステータス**: 有効

## 目的

このドキュメントは、gymini（筋トレ記録 × AIコーチングアプリ）の開発を統制する非交渉原則と基準を定義します。すべてのコード、設計判断はこれらの原則に従う必要があります。

## 原則階層

```
1. ビジネス原則（最優先）
   ↓
2. アーキテクチャ原則
   ↓
3. 開発手法原則
   ↓
4. 技術制約
```

優先度が高い原則が低い原則に優先します。

---

## 1. ビジネス原則（最優先）

### B-001: Privacy-by-Design

**原則**: ユーザーデータはブラウザのローカルストレージにのみ保存し、外部サーバーへ送信しない。AIへの送信はユーザーが明示的に許可したデータのみに限定する。

**適用範囲**: データ永続化、APIとの通信、状態管理

**検証方法**:

- [ ] ワークアウトデータがサーバーに送信されていないこと（ネットワークタブで確認）
- [ ] localStorage にのみデータが保存されていること
- [ ] AIチャット送信前に、ユーザーが確認できるデータ範囲が明示されること

**違反例**:

- ユーザーのトレーニングデータを分析のためにサーバーへ送信する
- AIチャット内容を第三者サービスにログとして送信する

**準拠例**:

- 全データを `localStorage.setItem()` で管理し、クライアント外に出さない
- Gemini API呼び出し時のプロンプトに含めるデータをユーザーが確認可能にする

---

### B-002: AI安全操作の確認優先

**原則**: AIが書き込み操作（ワークアウト保存・種目追加）を実行する前に、必ずユーザーに確認を求める。AIは自律的にデータを変更してはならない。

**適用範囲**: Function Calling、AIチャット機能

**検証方法**:

- [ ] AIがワークアウト保存・種目追加を提案した際に確認ダイアログが表示されること
- [ ] ユーザーが「キャンセル」した場合はデータが変更されないこと
- [ ] 確認なしにデータが書き込まれるパスが存在しないこと

**違反例**:

- Function Callingで確認なしにワークアウトを直接保存する
- チャットからの種目追加をユーザー確認なしに実行する

**準拠例**:

- AIが保存操作を提案 → 確認ダイアログ表示 → ユーザー承認後に実行
- 読み取り専用操作（記録参照）は確認不要

## 2. アーキテクチャ原則

### A-001: Library-First

**原則**: 可能な限り既存ライブラリを活用し、車輪の再発明を避ける。

**適用範囲**: すべての実装

**検証方法**:

- [ ] 新規実装前に既存ライブラリを調査したか
- [ ] 自作する場合の明確な理由があるか

**違反例**:

- ライブラリ調査なしで状態管理を自作実装（Zustandがすでにある）
- バリデーションライブラリが存在するのに独自実装する

**準拠例**:

- 状態管理には Zustand を活用
- UIコンポーネントには shadcn/ui + Radix UI を活用（Tailwind CSS でカスタマイズ）
- ルーティングには TanStack Router を活用（型安全なファイルベースルーティング）
- データフェッチ/キャッシュには TanStack Query を活用
- バリデーションには Zod を活用（型推論との統合）

---

### A-002: Client-Only Architecture

**原則**: バックエンドサーバーを設けず、すべての処理をクライアントサイドで完結させる。外部通信はGemini API呼び出しのみに限定する。

**適用範囲**: アーキテクチャ全体

**検証方法**:

- [ ] サーバーサイドの処理・エンドポイントが存在しないこと
- [ ] データ永続化がローカルストレージのみで行われていること
- [ ] 外部API呼び出しがGemini APIのみであること

**違反例**:

- データ同期のためにバックエンドAPIを追加する
- ユーザー認証のためにサーバーを追加する

**準拠例**:

- Vite による純粋な静的サイトとしてビルド・ホスティング
- Gemini APIはクライアントから直接呼び出す（BYOK）

## 3. 開発手法原則

### D-001: Test-First

**原則**: テストを先に書いてから実装する（TDD）。

**適用範囲**: すべてのコア機能（ドメインロジック・状態管理・ユーティリティ）

**検証方法**:

- [ ] 実装前にテストケースが作成されている
- [ ] テストカバレッジ ≥ 90%
- [ ] `vitest run --coverage` がカバレッジ基準を満たすこと

**違反例**:

- 実装完了後にテストを追加
- テストなしでのマージ

**準拠例**:

- Red → Green → Refactor のサイクルを遵守
- `describe` / `it` によるテストケース作成 → 実装 → リファクタリング

---

### D-002: ドキュメントの役割

**原則**: ドキュメントの役割を明確に分離し、メンテナンスコストを最小化する。

**適用範囲**: すべての機能・変更

**ドキュメント種別と責務**:

| 種別 | 場所 | 内容 | 更新義務 |
|:-----|:-----|:-----|:---------|
| **PRD** | `docs/prd/` | プロダクトビジョン・ユースケース・制約 | 機能追加・変更時に必須 |
| **ADR** | `docs/adr/` | アーキテクチャ判断記録（なぜこの技術・パターンを選んだか） | アーキテクチャ上の判断が生じた場合のみ（任意） |
| **テスト** | `src/` | 振る舞いの仕様（D-003参照） | 実装と常に同期 |

**ADR に書くもの / 書かないもの**:

- 書く: 「なぜ X を選んだか」「なぜ Y をしないか」など、コードから読み取れない判断・トレードオフ
- 書かない: コンポーネント構造、props/state の型定義、ファイル構成、実装詳細

**違反例**:

- コンポーネントの props 定義を ADR に書く
- 実装から乖離した PRD を更新せずに放置する

**準拠例**:

- 「localStorage vs IndexedDB」の採択理由を ADR に記録する
- 新機能追加時に `docs/prd/` の該当 PRD を更新する

---

### D-003: テストを仕様とする

**原則**: テスト（Vitest/Playwright）は実装の「いつでも実行可能な仕様書」である。テストが通れば仕様を満たしていると見なす。

**適用範囲**: すべての機能

**検証方法**:

- [ ] テストが通ること（`npm test`）
- [ ] ドキュメントとコードが乖離した場合、テストを正として扱うこと

**運用ルール**:

- `impl-status` フィールドの維持は廃止。テストの pass/fail が実装状態を表す。
- ADR とコードが乖離した場合、テストを正とする。ADR の更新は推奨だが任意。
- PRD とテストが矛盾した場合、自動的にどちらかを正とせず、**要検討フラグ**として扱う。

  | 原因 | 対応 |
  |:---|:---|
  | PRD が更新されないまま実装が変わった（意図的な仕様変更）| PRD を実態に合わせて更新する |
  | テストが誤って書かれた、またはプロダクト意図から外れた実装になっている | テストと実装を修正する |

  どちらのケースかは人間が判断する。「テストが通っているから PRD は無視」は許容しない。

**準拠例**:

- `describe('workout store', () => { it('セット追加で pending に変わる', ...) })` がテストとして振る舞いを仕様化する
- 仕様変更時はテストを先に更新し（D-001）、PRD も合わせて更新する（D-002）

## 開発標準

### コード品質

| 標準 | 要件 | ツール | 適用方法 |
|:-----|:-----|:-------|:---------|
| **Linting** | エラー・警告ゼロ | ESLint (eslint.config.js) | Pre-commit / CI |
| **型安全性** | TypeScript strict mode | TypeScript | CI |
| **テストカバレッジ** | ≥ 90% | Vitest + coverage-v8 | CI gate |
| **コンポーネント設計** | 単一責任、小さなコンポーネント | コードレビュー | PR review |

### ドキュメント

| 種別 | 場所 | 更新タイミング |
|:-----|:-----|:-------------|
| **PRD** | `docs/prd/` | 機能追加・変更時（必須） |
| **ADR** | `docs/adr/` | アーキテクチャ判断が生じた場合（任意） |

### テスト

| 標準 | 要件 | 適用方法 | 例外 |
|:-----|:-----|:---------|:-----|
| **ユニットカバレッジ** | ≥ 90% 行カバレッジ | CI gate | - |
| **ストアテスト** | Zustand ストアのすべての操作をカバー | 自動 | - |
| **エッジケース** | 境界条件・エラーケースをテスト | Code review | - |
| **E2E テスト** | 主要ユーザーフローをすべてカバー（必須） | Playwright / CI gate | - |

### セキュリティ

| 標準 | 要件 | 適用方法 | 頻度 |
|:-----|:-----|:---------|:-----|
| **APIキー保護** | Gemini APIキーをコードにハードコードしない | Lint / review | 各PR |
| **入力検証** | ユーザー入力（重量・回数・種目名）を検証 | コードレビュー | 各PR |
| **XSS防止** | dangerouslySetInnerHTML は使用しない | ESLint rules | 各コミット |

## アーキテクチャ制約

### 技術スタック

| レイヤー | 採用技術 | バージョン | 禁止事項 |
|:---------|:---------|:-----------|:---------|
| **UI フレームワーク** | React | ^19 | Vue, Angular, Svelte |
| **UIコンポーネント** | shadcn/ui + Radix UI | latest | MUI, Ant Design, Chakra UI |
| **スタイリング** | Tailwind CSS | ^4 | CSS-in-JS, styled-components |
| **ルーティング** | TanStack Router | ^1 | React Router, 自作ルーティング |
| **データフェッチ/キャッシュ** | TanStack Query | ^5 | SWR, 自作キャッシュ |
| **状態管理** | Zustand | ^5 | Redux |
| **バリデーション** | Zod | ^3 | Yup, Joi, io-ts |
| **ビルドツール** | Vite | ^8 | Webpack, Rollup（直接） |
| **PWA** | vite-plugin-pwa | latest | 手動Service Worker管理 |
| **ユニット/統合テスト** | Vitest + Testing Library | ^3 | Jest（Vitest 移行済み） |
| **E2E テスト** | Playwright | latest | Cypress, Puppeteer |
| **言語** | TypeScript (JSX) | strict mode | plain JavaScript |
| **AI API** | Google Gemini API | - | OpenAI, Anthropic等 |

**例外プロセス**: 技術スタックの変更はチーム承認後に ADR へ記録

**注記**: TanStack Router はファイルベースルーティングを使用し、`src/routes/` 配下にルートファイルを配置する。TanStack Start（SSR/SSGフレームワーク）は使用しない — 本プロジェクトは完全クライアントサイドアーキテクチャである（A-002）。

### モジュール構成

```
src/
├── routes/           # TanStack Router ルート定義（ファイルベース）
│   ├── __root.tsx    # ルートレイアウト（BottomNav等の共通UI）
│   ├── index.tsx     # / トレーニング画面
│   └── ...           # 各ページルート
├── components/       # UIコンポーネント（プレゼンテーション）
│   └── ui/           # shadcn/ui コンポーネント
├── stores/           # Zustandストア（状態管理・ビジネスロジック）
├── hooks/            # カスタムフック
├── lib/              # リポジトリ・ユーティリティ（localStorage CRUD等）
├── types/            # TypeScript型定義
└── schemas/          # Zod スキーマ定義（バリデーション・型生成）
```

**依存ルール**:

- `routes/` は `components/`, `stores/`, `hooks/`, `lib/`, `types/`, `schemas/` に依存可
- `components/` は `stores/`, `hooks/`, `lib/`, `types/`, `schemas/` に依存可
- `stores/` は `lib/`, `types/`, `schemas/` に依存可（UIに依存しない）
- `lib/` は `types/`, `schemas/` に依存可
- `schemas/` は外部依存なし（Zodスキーマ定義のみ）
- `types/` は外部依存なし（型定義のみ。Zodスキーマから推論された型は `schemas/` に配置）

## 意思決定フレームワーク

技術的トレードオフに直面した場合、以下の順序で優先順位付けします：

1. **プライバシー** - ユーザーデータは外部に出さない
2. **AI安全性** - AIの書き込み操作は必ずユーザー確認を経る
3. **正確性** - テストが通るか？
4. **シンプルさ** - 最もシンプルな解決策か？
5. **モバイル体験** - スマートフォンで快適に使えるか？
6. **保守性** - 保守可能か？

**タイブレーカー**: モバイルでの操作体験を優先する

## 4. 技術制約

### T-001: TypeScript Strict Mode

**原則**: TypeScript の strict mode を有効にし、`any` 型の使用を禁止する。

**適用範囲**: すべての TypeScript ファイル（`.ts`, `.tsx`）

**検証方法**:

- [ ] `tsconfig.json` で `"strict": true` が設定されている
- [ ] `any` 型が使用されていないこと
- [ ] 型推論が不十分な箇所は明示的に型を定義していること

**違反例**:

- `const data: any = JSON.parse(raw)` のような型なし変換
- `// @ts-ignore` コメントによる型エラー回避

**準拠例**:

- `const data: WorkoutRecord = JSON.parse(raw) as WorkoutRecord`
- 型ガード関数による実行時の型検証

---

### T-002: No Runtime Errors

**原則**: 実行時エラーを許容しない。特に localStorage アクセスや JSON パースは適切にエラーハンドリングする。

**適用範囲**: すべてのコード（特に localStorage/JSON/Gemini API）

**検証方法**:

- [ ] `JSON.parse()` を try-catch で囲んでいること
- [ ] localStorage アクセスが失敗した場合のフォールバックがあること
- [ ] Gemini API エラーが適切にハンドリングされていること
- [ ] 未処理の Promise rejection がないこと

**違反例**:

- `const data = JSON.parse(localStorage.getItem('workouts'))` のような未ガードのコード
- Gemini API エラーを握りつぶすだけのキャッチ

**準拠例**:

- try-catch + デフォルト値でのフォールバック
- エラー時のユーザーへのフィードバック（トースト通知等）

---

### T-003: Mobile-First UI

**原則**: スマートフォンでの使用を最優先としたUI設計。タップしやすいサイズ（最低44px）と親指操作を考慮したレイアウトを徹底する。

**適用範囲**: すべての UI コンポーネント

**検証方法**:

- [ ] タップターゲットが最低 44px × 44px であること
- [ ] 重要な操作（保存・追加）がスマホ下部エリアからアクセスしやすいこと
- [ ] タブナビゲーションが画面下部に固定されていること
- [ ] フォーム入力時にレイアウトが崩れないこと
- [ ] 生の `<button>` に `focus-ring` ユーティリティ（`src/index.css` 定義）を付与すること（キーボード操作時の可視リング）

**違反例**:

- 小さすぎるボタン（20px × 20px）
- PC前提のホバーエフェクトのみ
- raw `<button>` にフォーカスリングが無く、キーボード操作時に現在位置が不可視

**準拠例**:

- Tailwind の `min-h-[44px] min-w-[44px]` でタップターゲットを確保
- `active:` prefixによるタップフィードバック
- raw `<button>` に `focus-ring` クラス（共通ユーティリティ）を付与。shadcn `<Button>` はフォーカススタイル組み込み済みのため追加不要。詳細は `CLAUDE.md` の「キーボードフォーカス規約」を参照

---

### T-004: Design Token Consistency

**原則**: UIコンポーネントでは `src/index.css` に定義されたカスタムトークン（`gym-*`）を使用し、Tailwind 組み込みの汎用クラスを直接使用しない。トークンの追加・変更は `src/index.css` の `@theme` ブロックを唯一の変更箇所とする。

**適用範囲**: すべての UI コンポーネント（`.tsx` ファイル）

**デザイントークン一覧**（`src/index.css` の `@theme` ブロックが正）:

| カテゴリ | 使用するクラス | 禁止クラス（Tailwind組み込み） |
|:---------|:--------------|:-------------------------------|
| **カラー / 黒** | `text-gym-black`, `bg-gym-black` | `text-black`, `bg-black` |
| **カラー / 白** | `text-gym-white`, `bg-gym-white` | `text-white`, `bg-white` |
| **カラー / グレースケール** | `bg-gym-zinc-{50\|100\|200\|300\|400\|500\|600\|700\|800\|900}` 等 | `bg-zinc-*`, `text-zinc-*`, `border-zinc-*` |
| **カラー / アクセント** | `text-gym-accent`, `bg-gym-accent` | `text-red-*`, `bg-red-*` |
| **シャドウ / カード** | `shadow-soft` | `shadow-sm`, `shadow-md` （カード用途で） |
| **シャドウ / フロート** | `shadow-float` | インラインシャドウ（`shadow-[...]`）（フロート用途で） |

**ボーダーラジウス スケール**（用途別に固定）:

| 用途 | クラス | 対象コンポーネント例 |
|:-----|:-------|:--------------------|
| 行アイテム（密なレイアウト） | `rounded-xl` (12px) | CompletedSetRow, PendingSetRow |
| カード・モーダル | `rounded-[24px]` | ExerciseCard, WorkoutSummary, MonthCalendar, SectionCard |
| ピル・ヘッダー | `rounded-full` | AppHeader, BottomNav タブ |
| アイコンコンテナ | `rounded-[28px]` | IdleView アイコン背景 |

**フォントトークン**:

| 用途 | クラス | 適用例 |
|:-----|:-------|:-------|
| 見出し・数値 | `font-outfit` | 種目名、セット数値、ページタイトル |
| 本文・UI | （デフォルト: Sora） | 説明文、ラベル |
| 日本語専用 | `font-jp` | `年`, `月`, `kg`, `回` 等の単位ラベル |

**検証方法**:

- [ ] `grep -r 'className=.*\b\(bg\|text\|border\)-zinc-' src/` の出力が空であること
- [ ] カード系コンポーネントが `rounded-[24px]` + `shadow-soft` を使用していること
- [ ] フローティングUI（AppHeader 等）が `shadow-float` を使用していること
- [ ] `font-inter` / `font-sans` の直接指定がないこと

**違反例**:

```tsx
// NG: Tailwind 組み込みトークンの直接使用
<div className="bg-zinc-50 text-zinc-500 border-zinc-200 shadow-sm rounded-3xl">

// NG: インラインシャドウ（shadow-float を使うべき箇所）
<button className="shadow-[0_8px_30px_-6px_rgba(0,0,0,0.3)]">
```

**準拠例**:

```tsx
// OK: gym-* カスタムトークンを使用
<div className="bg-gym-zinc-50 text-gym-zinc-500 border-gym-zinc-200 shadow-soft rounded-[24px]">

// OK: shadow-float トークンを使用
<button className="shadow-float">
```

**例外**: `opacity` 修飾子との組み合わせ（例: `border-gym-zinc-200/50`）は許容。shadcn/ui 内部コンポーネント（`src/components/ui/`）は vendor コードのため適用対象外。

| 重大度 | 対応 | 例 |
|:-------|:-----|:---|
| **重大** | 即座にマージをブロック | AIが確認なしにデータ書き込み、プライバシー違反 |
| **主要** | 明示的な正当化が必要 | `any` 型の使用、バックエンド追加 |
| **軽微** | 現在のPRまたはフォローアップで修正 | 軽微なドキュメント更新、コード整理 |

### 例外プロセス

原則の遵守が不可能な場合：

1. **文書化**: ADR にトレードオフを記載
2. **正当化**: なぜ原則に従えないか説明
3. **緩和**: 補償統制を説明
4. **レビュー**: レビュアーから承認を得る
