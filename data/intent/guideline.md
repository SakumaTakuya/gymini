# 意図定義ガイドライン（Phase 0）

gymini 意図ルーティング PoC の学習データ・評価データ作成のためのアノテーション基準。
意図定義の正は PRD `docs/prd/intent-router/index.md` とし、境界ケースの判定基準は本ガイドラインを正とする（PRD §1）。

- 対象データ: `train.jsonl`（学習用）、`eval.jsonl`（評価用）
- 形式: 1行1JSON `{"text": "...", "labels": ["record"]}`。ラベルはマルチラベル（複数可）。
- 分類は「ユーザーが何をしてほしいか」だけを見る。アプリの状態（セッションがアクティブかどうか、キーの有無など）はラベルに影響させない。状態に応じた実行可否はルーティング側の責務（PRD FR_004 の `SESSION_NOT_ACTIVE` 案内など）。

---

## 1. 意図の定義

### `record`（記録）

- **定義**: 実施した（または実施中の）トレーニング内容の申告。種目・重量・回数・セット数の入力を意図する発話。
- **ルーティング先**: 数値抽出 → 種目照合 → セッション draft へ即時挿入（PRD FR_004）。
- **典型的な手がかり**:
  - 種目名＋数値（重量・回数・セット数）の組み合わせ。「ベンチ60kgで10回3セット」
  - 完了・遂行の表現。「スクワット終わった、80kg×5」「デッド140キロ引けた」
  - 数値がなくても種目の実施申告は record。「スクワット終わった」「ベンチやった」
  - 自重種目は重量がなくてよい。「懸垂10回3セット」
- **含まないもの**: 過去の記録についての質問（→ `history`）、既存記録の直し（→ `edit`）、これからやる予定の宣言（→ `other`）。

### `history`（履歴参照）

- **定義**: すでに記録された過去のデータについての照会・表示要求。
- **ルーティング先**: 端末内データ検索 → 表示。
- **典型的な手がかり**:
  - 過去を指す語＋疑問・表示要求。「昨日ベンチ何kgだった？」「先週の脚の日いつ？」「昨日の記録見せて」
  - 自己ベスト・頻度・回数など蓄積データへの質問。「デッドリフトの自己ベスト教えて」「先月何回ジム行った？」
  - 数値が含まれていても、照会が目的であれば history。「ベンチプレス60kgで記録した日いつ？」
- **含まないもの**: 終わったトレーニングの申告（→ `record`。§2 の record vs history を参照）。

### `advice`（アドバイス）

- **定義**: トレーニングに関する助言・判断・知識を求める発話。LLM の応答を必要とする相談全般。
- **ルーティング先**: LLM（キーがある場合のみ。キーなしの場合は設定への案内、PRD FR_002）。
- **典型的な手がかり**:
  - 重量・回数・メニューなどの判断を求める疑問。「次は何kgにすべき？」「回数と重量どっちを優先すべき？」
  - 遂行可能性の相談。「80kgいけるかな」
  - 痛み・フォーム・効きに関する申告と相談。「肩が痛いけどどうする？」「ベンチで胸に効いてる感じがしない」「スクワットでかかとが浮く」
  - 知識の質問。「プロテインはいつ飲むのがいい？」「セット間の休憩はどれくらいがいい？」
- **含まないもの**: アプリの操作方法・設定の質問（→ `other`）、単なる体調・感想のつぶやき（→ `other`。§2 の advice vs other を参照）。

### `edit`（修正・削除）

- **定義**: すでに存在する記録（セッション draft 内の種目・セット）に対する修正・削除・取り消しの指示。
- **ルーティング先**: 対象記録の特定 → 通常カードへの誘導（PRD FR_005）。プログラム経由で draft を直接書き換える経路は作らない。
- **典型的な手がかり**:
  - 誤りの指摘＋正しい値。「さっきのベンチ、60kgじゃなくて65kgだった」「回数は8回じゃなくて10回」
  - 削除・取り消しの指示。「最後のセット消して」「今の入力ミス、なかったことにして」
  - 対象の指示語（さっきの／最後の／直前の／今の）＋変更系の動詞（直して、消して、取り消して、訂正、変更）。
- **含まないもの**: 新規の記録申告（→ `record`）、過去記録の閲覧（→ `history`。「さっきの記録見せて」は history）。

### `other`（その他）

- **定義**: 上記4意図のいずれにも当たらない発話。雑談、挨拶、感想、予定の宣言、アプリの操作・設定の質問など。
- **ルーティング先**: 定型応答（キーがある場合は LLM も可。キーなしでは定型応答のみ、PRD FR_003）。
- **典型的な手がかり**:
  - 挨拶・相づち・感謝。「こんにちは」「ありがとう」「あ」
  - 感想・体調の申告のみで助言を求めていないもの。「疲れたー」「筋肉痛で階段がつらい」
  - 予定・意思の宣言。「今日はオフにする」「明日は脚の日だ」
  - 体重など種目実施以外の申告。「体重が2キロ減った」
  - アプリの使い方の質問。「記録をエクスポートできる？」「設定はどこから開くの？」
  - 無関係な話題、意味の取れない入力。
- **排他ルール**: `other` は他のラベルと併記しない（§3）。

## 2. 境界ケースの判定基準

### 共通の判定軸

迷ったら次の順で見る。

1. **既存の記録を変える指示か** → `edit`（数値の正誤を言い直す場合は特に注意）。
2. **過去のデータを求めているか（照会・疑問・表示要求）** → `history`。
3. **実施内容の申告か（新しいデータを入力している）** → `record`。
4. **判断・助言・知識を求めているか** → `advice`。
5. **どれでもない** → `other`。

キーワード単体では決めない。「昨日」「さっき」などの時間語も、疑問形も、それ単独では決定打にならない。文全体の目的で判定する。

### record vs history

- 判定軸は「データを**求めている**か」「データを**申告している**か」。
- 過去形でも申告なら record。「ベンチ60kgやった」「昨日ベンチ60kgで10回やった、記録して」はいずれも record（遡っての記録申告）。
- 疑問形で蓄積データを尋ねれば history。「昨日ベンチ何kgだった？」。
- 数値が入っていても照会なら history。「ベンチ70kgで記録したのいつだっけ」。
- 比較の質問（「前回より増えた？」）は、申告部分があっても照会を含むため `history` も付ける（マルチラベル。§3）。

### record vs edit

- 判定軸は「**新しい**実施の申告か」「**既存**記録への変更指示か」。
- 正しい値の言い直し（「〜じゃなくて〜だった」）、間違いの明示（「〜の間違い」「入力ミス」）、削除・取り消しは edit。数値が具体的でも record にはしない。
  - 「70kgで5回」→ record／「さっきの70kgの間違い」→ edit
- 対象への言及がなく、単に実施内容を述べているだけなら record。たとえ直前に似た記録があっても、文面に対象指示や変更の意図がなければ edit にしない。

### record vs advice

- 判定軸は「申告（断定）か、判断の相談（疑問・迷い）か」。
- 遂行できた事実の報告は record。「80kgいけた」。
- 遂行可能性や次の一手を尋ねれば advice。「80kgいけるかな」「次は重量上げるべき？」。
- 両方を含む文はマルチラベル（§3）。「60kgで10回やった、次どうすればいい？」→ `record` + `advice`。

### record vs other

- 「〜の日だ」「〜やるつもり」などの予定・宣言は record ではない（実施の申告ではない）。→ other。
- 種目の実施を終えた・行ったことが読み取れれば、数値がなくても record。

### history vs edit

- 判定軸は「見るだけか、変えるか」。
- 「さっきの記録見せて」「確認したい」は history。「さっきの記録消して」「直して」は edit。

### history vs advice

- 過去データの照会は history。照会に加えて「次どうするか」の相談があれば `history` + `advice` のマルチラベル。「前回ベンチ何kgだった？次は増やせそう？」

### advice vs other

- トレーニングの技術・判断・体への影響に関する相談は、疑問形でなくても advice（LLM が応答すべき内容）。「肩が痛い」「胸に効いてる感じがしない」など。
  - 特に痛みの申告は、安全面からも advice として LLM 応答に回す。
- 一方、助言を求めていない感想・体調のつぶやきは other。「疲れたー」「筋肉痛で階段がつらい」。
- アプリの操作・設定・機能の質問は、疑問形でも advice ではなく other。「通知設定はどこ？」。

### edit vs other

- 「やっぱり」のような語があっても、記録への変更指示がなければ other。「やっぱり今日は休む」は other。
- 変更の対象（記録・セット・種目）が文脈上明確に記録を指す場合のみ edit。

## 3. マルチラベルの付け方

- 1つの発話に複数の意図が**独立して**含まれれば、すべて付ける。ラベルの数に上限は設けないが、実データでは2つまでが大半を占める想定。
- 主な組み合わせ:
  - `record` + `advice`: 実施の報告＋次の相談。「デッド150kg引けた、次は160目指せるかな」
  - `history` + `advice`: 過去の照会＋今後の相談。「前回ベンチ何kgだった？次は増やせそう？」
  - `record` + `history`: 実施の報告＋過去との比較の照会。「ベンチ60kg10回やった、前回より回数増えた？」
- 処理順（記録を先に処理し、続けてアドバイスへ）はルーティング側の仕様であり、ラベルの並び順には意味を持たせない。
- `other` は排他。他のラベルが1つでも付く発話には `other` を付けない。挨拶などが混ざっていても、実質的な意図があればそちらだけを付ける。「おはよう、ベンチ60kg10回やった」→ `record` のみ。
- 片方の意図が単なる相づち・前置きにすぎない場合は付けない。「（相談の前置きとして）昨日さ、…」のように、照会の実質がない時間語だけで `history` は付けない。

## 4. 表記ゆれの扱い

表記ゆれは「分類を変えない」ことを原則とする。同じ意味内容であれば、表記が違っても同じラベルを付ける。データには意図的に以下のバリエーションを混在させる。

### 数字・単位

- 半角／全角: 「60kg」「６０kg」「８回」
- 単位の表記: kg／キロ／キログラム、単位なし（「ベンチ60で10回」）
- 回数・セット: 「10回」「10reps」「10レップ」、「3セット」「×3」、「80kg×5」
- 小数: 「62.5kg」「17.5キロ」
- 漢数字・口語は少数でよい（「十回」など）。

### 種目名の略称・別名

| 正式名 | データに混ぜる表記 |
| --- | --- |
| ベンチプレス | ベンチ、BP、ベンチプレス |
| スクワット | スクワ、スクワット |
| デッドリフト | デッド、デッドリフト、DL |
| ショルダープレス | 肩プレス、ショルダープレス、肩 |
| ラットプルダウン | ラットプル、ラットプルダウン、ラット |
| レッグプレス | レッグプレス |
| 懸垂 | 懸垂、チンニング、チン |
| アームカール | カール、アームカール |
| その他 | ダンベルプレス、インクラインベンチ、ディップス、ローイング、ヒップスラスト、ブルガリアンスクワット、カーフレイズ、プランク なども適宜使う |

- 部位だけの言及（「胸の日」「脚トレ」）も自然な範囲で混ぜる。

### 文体

- メモ書き（「ベンチ 60 10回 3セット」）、句読点なし、感嘆・絵文字・語尾の口語（「〜やったー」「〜だっけ」）を混ぜる。
- 誤字は学習データにごく少量だけ許容するが、評価セットには入れない（評価セットは人手確認済みの清潔な文とする）。

---

## 5. データ作成上の注意

- `train.jsonl` と `eval.jsonl` で、文面レベルで同一の文を重複させない。数値や種目違いの類似文は許容するが、言い回しもできるだけ分散させる。
- 評価セットは、各意図の典型例だけでなく、§2 の境界ケース（迷いやすいペア）を厚めに入れる。
- 1発話が長文になりすぎないようにする。実際の入力欄の発話らしく、原則1〜2文まで。
- ラベル付けに迷う文は、§2 の判定軸で決め、無理に曖昧な文を評価セットへ入れない（入れると評価基準そのものがぶれる）。
